# Run the unchanged app

Regression-support route only (not the primary kit tutorial); these native sandbox steps have not been run. Review ACCESS.md and every command before approving.
These files were generated by `sbx_langchain_kit.py direct` from the reviewed app and answers. They are pre-generated regression-support fixtures: `sbxenv.yaml`, the filtered `workspace/` snapshot, `setup-deps.sh` copied from the helper template, ACCESS.md and this runbook. The [helper tests](https://github.com/shelajev/langchain-policy-lab/blob/main/skills/langchain-sandbox-kit/tests/test_helper.py) regenerate these fixtures from `examples/<app>/` and `examples/<app>.answers.json` and compare every output byte. Run `bash scripts/check-skill.sh` from the repository root for that check. The separate [check-direct.sh](https://github.com/shelajev/langchain-policy-lab/blob/main/scripts/check-direct.sh) builds an ordinary-container probe from a raw fixture; it does not run these native steps or validate SBX confinement. These are maintainer regression fixtures, not a fallback for failed kit builds. Learners should follow the kit tutorial and use `generate`.
Run host commands from this control directory. `sbxenv.yaml` selects a pinned shell workload, mounts `workspace/`, and names the sandbox `ticket-triage-kit`; every `--sandbox` command below uses that same name. Stop if the name is already in use; do not change only one command's target.
If a provider credential was selected, `sbxenv.yaml` sets its SDK environment variable to a `proxy-managed` placeholder, never the real key. The host secret command below stores that service value only after the named sandbox exists.
`workspace/` contains the selected app, data and lock files. `setup-deps.sh` downloads checksum-verified uv from GitHub releases inside the guest, then `uv sync --locked` creates `.venv` in that mounted workspace.
No generated mixin is needed. An allow request adds to composed policy and does not cancel broader inherited grants.
Choose offline or live mode before Step 1. For a supported fake/offline model run, skip the live-only secret and provider-host commands; temporary dependency-download access is still needed for setup. A fake model does not disable separately requested HTTP tools.

## 1. Host: inspect and create

```bash
sbx policy ls
sbx secret ls
sbx env plan ./sbxenv.yaml
```

Pause and review the plan before creating anything. Confirm the declared workload, workspace and reviewed resources. Then create the environment:

```bash
sbx env create ./sbxenv.yaml
```

For separately approved live provider use only, bind the credential after creation. Skip this block for fake/offline model checks:

```bash
sbx secret set google --sandbox ticket-triage-kit
```

Review the plan and any approval prompt before continuing. It should select only the declared workload, workspace and reviewed resources. Additional credential-binding prompts are unverified: stop and review any unexpected scope; these commands create no global binding. The secret step is unnecessary for a fake/offline run that needs no key.

## 2. Host: scoped bootstrap and runtime policy

The `example.com` deny below creates the resolvable negative control tested in Step 5. Other denies come from ACCESS.md.

```bash
sbx policy allow network --sandbox ticket-triage-kit files.pythonhosted.org
sbx policy allow network --sandbox ticket-triage-kit github.com
sbx policy allow network --sandbox ticket-triage-kit pypi.org
sbx policy allow network --sandbox ticket-triage-kit release-assets.githubusercontent.com
sbx policy deny network --sandbox ticket-triage-kit example.com
sbx policy deny network --sandbox ticket-triage-kit hooks.example.invalid
sbx policy deny network --sandbox ticket-triage-kit status.example.invalid
sbx env exec ./sbxenv.yaml -- pwd
sbx env exec ./sbxenv.yaml -- ls -la
sbx env exec ./sbxenv.yaml -- test -f pyproject.toml
```

Stop here. `pwd` prints the guest's resolved working directory; the YAML's host-relative `workspace/` path does not specify that guest path. `test -f` must succeed (exit 0). Compare the guest listing with the local reviewed `workspace/` before setup; stop if the expected project files are missing.

For separately approved live provider use only, add these provider-host requests. Skip this block for fake/offline model checks:

```bash
sbx policy allow network --sandbox ticket-triage-kit generativelanguage.googleapis.com
```

Only after the workspace check, run setup inside the guest:

```bash
sbx env exec -i ./sbxenv.yaml -- sh < setup-deps.sh
```

The reviewed setup script checks uv's release hash and runs uv sync --locked in that workspace. Package build hooks execute inside the sandbox. Proxy credentials use a sentinel environment value; real keys are injected only on supported matching requests.

## 3. Host: remove temporary grants

```bash
sbx policy rm network --sandbox ticket-triage-kit --resource github.com
sbx policy rm network --sandbox ticket-triage-kit --resource release-assets.githubusercontent.com
sbx policy rm network --sandbox ticket-triage-kit --resource pypi.org
sbx policy rm network --sandbox ticket-triage-kit --resource files.pythonhosted.org
sbx policy ls
```

Inspect effective policy on the host after removing temporary bootstrap rules. Do not claim other hosts are denied if inherited host or org rules allow them.

## 4. Host: execute inside the sandbox

The reviewed command below selects `--fake-model`; for these examples it makes no model call and needs no model key. Review app-specific settings separately before choosing a live variant.

Reviewed launch command:

```bash
sbx env exec ./sbxenv.yaml -- .venv/bin/python -m ticket_triage.app --ticket data/tickets/t-101.json --fake-model
```

Run the shown fake-model command from the host. The live variant is outside this fixture's reviewed launch; follow the app documentation and obtain a new launch review before omitting its fake flag.
For an interactive shell use `sbx env run ./sbxenv.yaml`, activate the guest `.venv`, and run the corresponding reviewed app command there.

Compare output and app-specific live-mode flags with the reviewed app documentation. The repository [single-file example](https://github.com/shelajev/langchain-policy-lab/tree/main/examples/single-file-agent) and [ticket-triage example](https://github.com/shelajev/langchain-policy-lab/tree/main/examples/ticket-triage) document their fake-model checks and live prerequisites. Do not treat a successful process exit as answer validation.

## 5. Host: denied operation and origin control

```bash
sbx env exec ./sbxenv.yaml -- python3 -c "import urllib.request; urllib.request.urlopen('https://example.com', timeout=10)"
sbx policy log ticket-triage-kit
```

First confirm from the host that https://example.com resolves and responds normally. Then match the guest failure to an example.com denial in this sandbox's policy log; DNS, TLS or timeout errors alone do not prove a policy block. Use a resolvable destination for this control; a DNS failure is not proof of a sandbox-policy block.
Verify inside the sandbox that `.env` and private/ are absent without printing secrets. Build or container checks do not prove this SBX runtime boundary.

## 6. Host: cleanup

```bash
sbx env rm ./sbxenv.yaml
```

Use `sbx policy ls` and `sbx secret ls` on the host to review leftovers; remove only this run's scoped entries. Cloud sandboxes are unverified here and have no host workspace mount; cloud runs require an approved kit or bake transfer plus separate cloud credentials and policy.
