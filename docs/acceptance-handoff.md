# Host acceptance: native sandbox run of the single-file kit

This page defines the native Docker Sandboxes verification runbook for `examples/single-file-agent-kit/` and separates it from the historical 2026-11-13 host observations. For the repository component map and CI scope, see [docs-team-handoff.md](docs-team-handoff.md); for the tutorial workflow, see [run-your-langchain-in-docker-sandboxes.md](run-your-langchain-in-docker-sandboxes.md); for dependency and spec provenance, see [provenance.md](provenance.md).

## Scope and verification status

Everything on this page targets `examples/single-file-agent-kit/` only. `examples/ticket-triage/` and `sample/` have not had native sandbox or live model runs, OpenAI and Anthropic have descriptor and mapping unit checks only, and cloud (`sbx --cloud`) and Docker Hub publishing flows are unrun.

The public source baseline for this record is `d51cc029`. The host results recorded at the end of this page are historical observations from 2026-11-13 at pre-public-history commit `aa2af15`. They document runtime behavior observed in that session and do not certify regenerated documentation or updated manifest hashes on the current baseline.

The clean-host workflow of entering a real scoped key interactively with `sbx secret set` and then executing a live model call has **not been verified**. The historical live call used a pre-existing global `google` secret, and a separate post-creation scoped-secret check used a synthetic invalid value.

## Pre-sandbox artifact and CI checks

`examples/single-file-agent-kit/` is generated by `skills/langchain-sandbox-kit` from `examples/single-file-agent/` and [single-file-agent.answers.json](../examples/single-file-agent.answers.json). The current [kit-manifest.json](../examples/single-file-agent-kit/kit-manifest.json) records each output path relative to the kit directory and its SHA-256 digest. The unit tests below regenerate the committed examples, compare all output bytes (including the manifest), and check generated output hashes. A manual alternative is to calculate each listed file's SHA-256 and compare it with its `outputHashes` entry.

For local checks, install `uv`, a usable Python 3.13.7 environment, a working Docker Engine/Buildx builder and `kit-tck` on PATH. Builds download pinned base images and locked dependencies; the composition probe uses the pinned shell image. The [contributor prerequisites](policy-lab-guide.md#prerequisites-and-downloads) describe tools, registry access and the pinned installer (`scripts/install-ci-tools.sh`, which builds `kit-tck` with Go). Use an authorized build environment; these checks need no native SBX daemon. Run both scripts below from the **repository root**. They verify the skill and built kit without launching a sandbox (distinct from native `sbx` checks):

- `bash scripts/check-skill.sh` ([check-skill.sh](../scripts/check-skill.sh)): runs the skill helper unit tests, which regenerate and compare committed examples (`explain` alone checks only `PERMISSIONS.md`).
- `bash scripts/check-single-file.sh` ([check-single-file.sh](../scripts/check-single-file.sh)): runs `explain`, builds the kit OCI artifact from its YAML descriptor and Dockerfile recipe with Buildx, validates the OCI output with `kit-tck` (19 conformance checks), and runs a composition probe that overlays the kit onto the pinned `docker/sbx-kit-shell:1.0.0` image and executes the [RUN.md](../examples/single-file-agent-kit/RUN.md) command offline, read-only, as uid 1000. Its app command is `/opt/single-file-agent-kit/venv/bin/python agent.py --fake-model` from `/opt/single-file-agent-kit/app`, and it asserts JSON equal to `{"category":"technical","ticket_id":"T-101"}`. That probe validates the overlay and entrypoint only; it is not evidence of sandbox network policy enforcement or proxy credential injection.

## Fresh verification runbook

Run this sequence from `examples/` on a host with `sbx` (syntax checked against v0.53.0) and a working local Docker Buildx plugin. A live scoped-key test additionally needs a valid Gemini API key and approval for the call's cost and data transfer; offline checks need no key. Confirm `docker buildx version` works in the same host client context used by `sbx`, because `sbx run --kit` builds local kit directories through host Buildx.

Invoke every `sbx` command below, including `sbx exec`, in the **host shell**. The command passed to `sbx exec` executes inside the guest; `-w /opt/single-file-agent-kit/app` sets that guest command's working directory. In the create command, `shell` selects the workload, `--kit` selects the generated mixin, and the final directory argument selects the workspace mounted into the guest. Reusing the generated directory as that workspace avoids mounting the original project; the app commands below execute the baked `/opt/single-file-agent-kit/app` copy, independently of files in the mounted workspace. The `google` secret provides the app's Gemini runtime key inside the sandbox proxy, separate from the coding agent's account.

Before creation, inspect `sbx secret ls` and `sbx policy ls` on the host. Bare `sbx secret ls` lists all scopes; `sbx secret ls --global --service google` restricts the listing to the global Google service. A result there means this is not a clean-host scoped-key test (v0.53.0 syntax). For a clean-host scoped-key test, no global `google` secret should be available to satisfy the call instead. If one exists, do not remove or alter it for this run: record that the host does not meet the clean-host precondition. For a global-backed run, skip the scoped `secret set` line below and qualify the live result as global-backed. To verify the clean-host scoped-key flow, use a separately authorized host/profile without a global `google` secret; do not certify that flow on this host. Also confirm no existing sandbox uses `single-file-agent-kit`. After creation, `sbx policy ls` shows a policy overview; use `sbx policy ls single-file-agent-kit --wide` for active rule details applying to this sandbox (v0.53.0 syntax). Compare those rows with the descriptor: the provider request should be allowed and no effective grant should allow `example.com` for this negative-control case. The matching target-specific policy log, rather than the overview alone, supplies the runtime observation.

Pre-creation inspection commands (on the host):

```bash
sbx secret ls
sbx secret ls --global --service google
sbx policy ls
sbx ls
```

The descriptor is `./single-file-agent-kit/single-file-agent-kit.yaml`; its provider host is `generativelanguage.googleapis.com` and its secret service is `google`.

This block is the intended runbook for a fresh verification, not a transcript of the 2026-11-13 host session. Run the commands individually, review `sbx policy ls` before interpreting the negative control, and verify both blocked and allowed hosts in `sbx policy log`.

```bash
sbx run --detach shell --kit ./single-file-agent-kit --name single-file-agent-kit ./single-file-agent-kit
sbx policy ls
sbx policy ls single-file-agent-kit --wide
sbx exec -w /opt/single-file-agent-kit/app single-file-agent-kit /opt/single-file-agent-kit/venv/bin/python agent.py --fake-model
sbx exec single-file-agent-kit sh -c 'test -z "$(find /opt/single-file-agent-kit -name .env -o -name private -o -name id_rsa)" && echo no-private-files'
sbx exec single-file-agent-kit /opt/single-file-agent-kit/venv/bin/python -c "import urllib.request; urllib.request.urlopen('https://example.com', timeout=10)"
sbx policy log single-file-agent-kit
sbx secret set google --sandbox single-file-agent-kit
sbx exec -w /opt/single-file-agent-kit/app single-file-agent-kit /opt/single-file-agent-kit/venv/bin/python agent.py
sbx policy log single-file-agent-kit
sbx rm single-file-agent-kit
sbx secret ls --sandbox single-file-agent-kit
```

| Check | Expected pass condition |
| --- | --- |
| Preconditions | No existing `single-file-agent-kit` sandbox; record whether a global `google` secret exists and follow the clean-host/global-backed branch above; review existing rules before creation |
| Create | Sandbox created detached from `./single-file-agent-kit`; record any CLI prompt to approve requested kit resources (none appeared in the historical run; its clean-host trigger and wording remain unverified) |
| Effective policy | Review existing and requested rules: if another grant allows `example.com`, this negative control cannot establish the intended default-deny case. Record the effective state; do not change global rules to manufacture it |
| Offline run | Exact stdout `{"category":"technical","ticket_id":"T-101"}` |
| Private files | `no-private-files`. This is a deployed-filesystem hygiene check: the clean source fixture contains no `.env`, `private/` or `id_rsa` canaries, so this result alone is not an adversarial exclusion test. Helper unit tests exercise synthetic private-file canaries separately |
| Denied host | Request fails and `sbx policy log` records a blocked `example.com` entry. The historical proxy returned HTTP 403; a DNS, TLS or timeout error alone is not proof. Adding an allow request in a kit does not make the composed sandbox policy exclusive; other grants can widen access, while denies win |
| Secret | `sbx secret set` prompts interactively for the key without `--token` |
| Live run | Stdout parses as JSON with `"ticket_id": "T-101"` and the target policy log records an allowed `generativelanguage.googleapis.com` entry. This observes a successful authenticated request on the allowed route; a policy-log allow by itself does not prove secret isolation. Review the descriptor's `google` proxy binding and `GOOGLE_API_KEY` placeholder separately; this runbook does not audit arbitrary extra guest environment configuration |
| Cleanup | `sbx rm` removes the sandbox and its scoped secret; the final scoped `secret ls` must show no retained secrets. Record the actual CLI output rather than assuming an empty-list format |

Cloud runs (`sbx --cloud run ... --kit`) and registry publishing are outside this runbook and remain unrun.

## Historical host observations (2026-11-13, `aa2af15`)

All entries below record observations from the 2026-11-13 host test on pre-public-history commit `aa2af15`. The historical commit is not publicly inspectable here. Native sandbox behavior on public baseline `d51cc029` and subsequent revisions is **unverified by this record** until the fresh runbook is executed on that exact revision. Do not treat the old pass or regenerated manifest as current native acceptance. For automated CI runs on the current revision, see [GitHub Actions](https://github.com/shelajev/langchain-policy-lab/actions).
